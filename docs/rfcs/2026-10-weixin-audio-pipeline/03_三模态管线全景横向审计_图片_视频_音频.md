# 三模态管线全景横向审计：图片 vs 视频 vs 音频

> **目的**：通过对 Hermes 内部三大非文本多模态输入（图片、视频、音频）的源码走查，揭示音频管线“落后于时代”的技术成因，为后续架构对齐提供标准参照物。

---

## 一、 源码级三模态处理架构矩阵

| 架构维度 | 🖼️ 图片管线 (Image Pipeline) | 🎬 视频管线 (Video Pipeline) | 🎙️ 音频管线 (Audio Pipeline - 重灾区) |
| :--- | :--- | :--- | :--- |
| **核心源码位置** | `agent/image_routing.py`<br>`gateway/run_inbound.py` | `tools/vision_tools.py`<br>`gateway/run_inbound.py` | `gateway/run.py`<br>`tools/transcription_tools.py` |
| **设计哲学** | **智能双轨制 (Dual-Track)**<br>嗅探大模型原生能力后自适应分流 | **彻底解耦 (Decoupled)**<br>保留原始文件，不设前置黑盒转换 | **僵化劫持 (Legacy Monolithic)**<br>强行在网关层抹杀声学多模态特征 |
| **入站预处理** | 自动嗅探：若主模型支持 Vision 则挂载像素；纯文本模型才调用辅助视觉前置转字 | **绝不自动转文字**<br>原始视频文件 100% 完整保留 | **无差别强制转文字**<br>无论模型是否具备音频能力，全走 STT |
| **交付给 Agent 的形态** | 注入 `native_image_paths` 原生像素，或注入详细画面描述 | 注入带路径的元数据笔记：<br>`[The user sent a video attachment: /path/video.mp4]` | **原始文件被隐匿**，仅塞入一段打上引号的识别文本 `"{transcript}"` |
| **底层专用分析工具** | **`vision_analyze`**<br>(支持图像全景、局部坐标 crop 放大问答) | **`video_analyze`**<br>(Base64 直喂 Gemini，同时解析画面与音轨) | **完全缺失 `audio_analyze` 工具**<br>(仅提供文字版 STT 与合成版 TTS) |
| **声学与美学感知力** | 像素空间推理 | 画面与音轨时空协同推理 | **彻底丧失**（调式、BPM、乐器在转字后全毁） |

---

## 二、 深度对比剖析

### 1. 图片管线的先进性借鉴（Image Pipeline）
- **动态能力感知**：
  在 `agent/image_routing.py` 中，`decide_image_input_mode` 会读取模型的实际 capabilities（或配置中的 `image_input_mode: native`）。如果当前模型是 Gemini 3.8 / Claude 3.5 等强视觉模型，图片像素直接挂载进请求体，不产生多余的转译开销；
- **防伪与健壮性**：
  通过 `_sniff_mime_from_bytes` 检查 Magic Bytes 文件头，杜绝扩展名伪造；同时支持 `_try_shrink_image_parts_in_messages` 响应式图片自适应缩放（防范单张超 5MB 被上游拒绝）。

### 2. 视频管线的解耦借鉴（Video Pipeline）
- **把决策权交给智能体**：
  在 `gateway/run_inbound.py` 中，网关只负责下载与安全校验，通过 `_prepend_inbound_media_file_notes` 告知智能体文件的本地绝对路径与文件名；
- **音视频联合感知**：
  在 `tools/vision_tools.py` 的 `video_analyze_tool` 中，提示词直接要求 `"including visual content, motion, audio cues, text overlays"`，将整包视频作为 Data URL 交给 Gemini 的原生音视频多模态接口处理，真正发挥了多模态大模型的声学理解力。

### 3. 音频管线的致病根源（Audio Pipeline）
- **十年前的“对讲机”偏见**：
  设计者默认音频输入必然是“人类说话对讲”，因而必须“先过语音识别变成 Text”才能进 LLM；
- **时代严重脱节**：
  完全忽视了现代前沿模型（Gemini 2.0/3.8 Flash、GPT-4o Audio）早已具备**原生端到端音频多模态输入（Audio-in）**能力的事实；
- **粗暴吞噬原件**：
  不仅强制调用效果极差的本地小 Whisper 模型（CPU 单核跑 74M 参数 base 模型），而且在转写后将原文件的路径和凭据全部隐匿，导致哪怕挂载了最强大的多模态主模型，也只能沦为看“幻觉乱码”的瞎子和聋子。

---

## 三、 结论

Hermes 框架要实现真正的统一多模态智能体，**音频管线必须全面看齐视频管线的解耦设计**，并将控制权交还给具备多模态能力的大模型。
